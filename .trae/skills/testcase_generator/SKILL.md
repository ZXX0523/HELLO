# 测试用例生成器

## 目标

根据需求稳定测试点生成结构化测试用例，覆盖正向、反向、边界场景，支持多种测试设计方法和输出格式，提供智能测试用例管理功能。

## 角色定位

作为拥有 10 年 + 企业级软件测试经验的资深测试工程师，掌握 AI 领域知识，精通测试和代码逻辑，擅长从需求文档和技术文档中全维度提取功能点、业务规则、约束条件、异常分支、边界场景、依赖逻辑，设计高覆盖率、无遗漏、可落地执行的测试用例。

## 业务注意点说明

- 当需求文档中有指定业务线/品牌/学科时,反向用例就是非该业务线时不显示该功能点或原有功能点保持不变。

## 核心原则

- **策略指导：** 提供判断标准，而非强制数量
- **场景驱动：** 基于实际场景复杂度生成用例
- **数据具体：** 测试数据必须具体，不用占位符
- **可验证性：** 预期结果必须明确可验证
- **灵活性：** 支持多种输入输出格式
- **可扩展性：** 支持自定义测试用例模板
- **智能管理：** 提供测试用例版本控制和复用功能
- **质量保证：** 内置测试用例质量评估机制
- **强制图片解析（关键）：**
  - **必须提取并分析需求文档中的所有图片**
  - **测试数据必须来源于图片中的真实数据**（如：学员ID、课包ID、liveid、时间、金额等）
  - **界面验证必须基于截图中的实际布局**（字段名称、按钮位置、表格列名等）
  - **业务流程必须基于流程图中的实际步骤**
  - **禁止凭空想象功能或数据**

## 核心测试设计方法

### 1. 等价类划分法

将输入数据划分为若干等价类,从每类中选取代表性数据测试。

**应用示例:**
**用户名密码登录**

**输入项:** 用户名、密码

**用户名等价类:**

- 有效: \[6-20字符,字母数字下划线] → "test\_user123"
- 无效: \[<6] "ab" | \[>20] "verylongusername12345" | \[特殊字符] "user\@name" | \[空] ""

**密码等价类:**

- 有效: \[8-20字符,含大小写+数字] → "Test1234"
- 无效: \[<8] "Test12" | \[缺大写] "test1234" | \[空] ""

**生成原则:** 一次测试一个等价类,其他保持有效

### 2. 边界值分析法

边界是最容易出错的地方。

**边界三点法:** 离点(min-1) | 上点(min) | 内点(中间值) | 上点(max) | 离点(max+1)

**应用示例:**
**用户名长度 6-20 字符:**

- 离点-下: 5字符 "abcde" → 失败
- 上点-下: 6字符 "abcdef" → 成功
- 内点: 13字符 "test\_user\_123" → 成功
- 上点-上: 20字符 "test\_user\_1234567890" → 成功
- 离点-上: 21字符 "test\_user\_12345678901" → 失败

**0 值法:**

**应用场景:** 部分属性为0 后则不再显示后续操作的场景（如学员详情中，课时为0 则不再显示课时明细链接）

### 3. 因果图法

通过分析输入条件之间的因果关系，生成测试用例。

**应用场景:** 输入条件之间存在逻辑关系（如 AND、OR、NOT）的场景

**应用示例:**
**购物车结算**

**输入条件:**

- A: 商品库存充足
- B: 支付方式可用
- C: 地址信息完整

**输出结果:**

- X: 结算成功
- Y: 结算失败

**因果关系:**

- A ∧ B ∧ C → X
- ¬A ∨ ¬B ∨ ¬C → Y

### 4. 判定表法

将输入条件和输出结果以表格形式列出，生成测试用例。

**应用场景:** 输入条件较多且组合复杂的场景

**应用示例:**
**用户登录验证**

| 条件 | 用户名正确 | 密码正确 | 验证码正确 | 结果       |
| -- | ----- | ---- | ----- | -------- |
| 1  | Y     | Y    | Y     | 登录成功     |
| 2  | Y     | Y    | N     | 验证码错误    |
| 3  | Y     | N    | Y     | 密码错误     |
| 4  | N     | Y    | Y     | 用户名错误    |
| 5  | N     | N    | Y     | 用户名和密码错误 |

### 5. 场景法

基于用户实际使用场景生成测试用例。

**应用场景:** 业务流程复杂的场景

**应用示例:**
**电商购物流程**

**主场景:**

1. 用户登录
2. 浏览商品
3. 加入购物车
4. 结算
5. 支付
6. 订单确认

**备选场景:**

- 登录失败
- 商品无库存
- 支付失败
- 地址信息不完整

### 6. 错误推测法

基于经验和直觉推测可能的错误场景。

**应用场景:** 无法通过其他方法覆盖的异常场景

**应用示例:**
**文件上传功能**

- 文件大小超过限制
- 文件格式不支持
- 网络中断
- 服务器存储空间不足
- 文件名包含特殊字符

### 7. 用例数量判断

不强制数量，根据场景复杂度自适应调整。

**判断标准：**

- **输入项数量：** 输入项越多，用例越多
- **业务规则复杂度：** 规则越复杂，用例越多
- **风险等级：** Critical 和 High 需要更多用例
- **测试关注点：** 关注点越多，用例越多
- **测试类型：** 不同测试类型需要不同数量的用例

**推荐用例数量范围：**

- **简单场景：** 3-5个用例
- **中等场景：** 5-10个用例
- **复杂场景：** 10-20个用例

### 5. 字段说明

markdown文件root节点：直接使用【需求名称】，不需要拼接其他字符，适用生成的所有用例文件

**优先级：** P0-P2（必填）

- P0（核心必测）：系统核心业务流程、主功能、数据准确性的测试点，不通过则功能无法正常使用；冒烟用例仅从P0优先级中选取，聚焦最核心、最基础的流程验证，确保系统能正常启动、核心功能可正常使用。
- P1（重要验证）：影响功能使用体验、辅助功能正常运行的测试点，不通过不阻断核心流程但影响使用；此类用例不设为冒烟用例。
- P2（次要检查）：界面展示、非核心交互、边缘场景的测试点，不通过对业务流程无实质影响；此类用例不设为冒烟用例

**\反向-：** 反向用例标记（可选）

**测试类型：** 功能、接口、性能、安全、兼容、易用、安装部署、可靠、本地化、可维护、可扩展、配置（12选1）

**前置条件：** 测试前的准备工作

**测试步骤：** 操作步骤，每个步骤占一行

**预期结果：** 期望的结果，与步骤一一对应

## 用例生成流程

### Step 1: 准备上下文

1. 检测 requirement 目录下的需求文档格式（PDF 或 DOCX）
2. 读取需求文档内容，包括文本和图片
3. **【强制】解析需求文档中的图片**（必须执行，不可跳过）：
   - 提取所有嵌入图片（PNG、JPG、JPEG 等格式）
   - 识别图片类型：界面截图、流程图、架构图、示例数据等
   - 保存图片到临时目录供后续分析使用
   - **必须分析图片内容并用于生成测试用例**
4. 读取 requirement 目录下的技术设计文档（如果存在），包括其中的图片
5. 读取配置文件（如果存在）
6. 提取需求文档文件名作为输出文件前缀
7. 加载自定义模板（如果有）

### Step 2: 理解测试点

从需求文档和技术设计文档中提取测试点：

- 分析需求文档文本内容，识别功能点和业务规则
- **【强制】必须分析需求文档中的图片**，提取以下信息：
  - **界面截图**：提取页面布局、字段名称、按钮位置、数据格式、消息内容、提醒文案等
  - **流程图**：提取业务流程步骤、判断条件、分支逻辑等
  - **示例数据**：提取真实数据值（ID、名称、时间、金额、组织架构路径等）
  - **架构图**：提取系统模块关系、数据流向、组织架构层级等
- **【强制】基于图片内容补充测试用例**：
  - 验证界面截图中的字段是否在预期结果中体现
  - 使用图片中的真实数据作为测试数据
  - 根据截图中的消息格式编写预期结果
  - 根据组织架构图验证权限和分组逻辑
- 将图片信息与文本信息结合，形成完整的需求理解
- **【强制】测试数据必须使用图片中的真实数据**，禁止使用占位符
- 分析技术设计文档，了解技术实现细节
- 确定测试类型和优先级
- 识别核心功能，确定冒烟用例

### Step 3: 识别输入项

- 列出所有输入项（字段、参数、操作等）
- 识别输入项的约束条件
- 确定输入项之间的逻辑关系
- 分析可能的异常场景

### Step 4: 选择测试设计方法

根据场景复杂度和测试类型选择合适的测试设计方法：

- 简单场景：等价类划分法 + 边界值分析法
- 复杂场景：因果图法 + 判定表法
- 流程场景：场景法
- 特殊场景：错误推测法

### Step 5: 生成测试用例

基于选择的测试设计方法生成测试用例：

- 核心功能：覆盖有效等价类
- 异常场景：覆盖无效等价类
- 边界条件：覆盖边界值
- 组合场景：覆盖输入项组合
- 流程场景：覆盖完整业务流程
- 异常场景：覆盖可能的错误情况

### Step 6: 验证测试用例

- 检查测试用例的完整性
- 检查测试数据的具体性
- 检查预期结果的可验证性
- 检查测试用例的覆盖度
- 评估测试用例的质量

### Step 7: 生成用例文件

- 将所有测试用例生成到一个文件中
- 文件命名为：{需求文档文件名}\_test\_cases.md
- 按照指定格式编写用例
- 确保测试数据具体、预期结果可验证
- 按模块和功能点组织用例结构

## 高级功能

### 1. 自定义模板

支持用户自定义测试用例模板，通过修改 templates 目录下的模板文件或在 CLAUDE 文件中配置模板。

### 2. 批量生成

支持批量生成多个测试点的测试用例，自动处理多个 ITEM 和 POINT，支持并行生成以提高效率。

### 3. 测试用例评审

生成测试用例后，提供评审功能，检查测试用例的质量和覆盖度，生成评审报告。

### 4. 测试执行跟踪

支持在测试用例中添加执行状态和结果，便于跟踪测试执行情况，生成测试执行报告。

### 5. 智能测试数据生成

根据输入项的约束条件，智能生成符合要求的测试数据，提高测试数据的质量和覆盖度。

### 6. 测试用例质量评估

内置测试用例质量评估机制，从完整性、可验证性、覆盖度等方面评估测试用例的质量。

### 7. 需求文档图片解析（强制）

**必须解析需求文档中的所有图片**，这是生成准确测试用例的关键步骤：

**图片提取流程：**

1. **自动提取**：从 PDF/DOCX 文档中提取所有嵌入图片
2. **图片分类**：
   - 界面截图：识别页面布局、功能模块、数据表格
   - 流程图：识别业务流程、判断节点、分支路径
   - 架构图：识别系统组件、数据流向、接口关系
   - 示例数据：识别真实数据值、字段格式、计算逻辑
3. **内容识别**：
   - 读取截图中的文字内容（OCR）
   - 识别表格结构和数据
   - 提取界面元素（按钮、输入框、标签页等）

**图片信息应用：**

- **测试数据**：必须使用图片中的真实数据（ID、名称、时间、金额等）
- **操作步骤**：必须按照截图中的实际界面元素编写
- **预期结果**：必须验证截图中显示的实际字段和布局
- **业务流程**：必须遵循流程图中的实际步骤

**禁止行为：**

- 禁止忽略需求文档中的图片
- 禁止凭空想象界面布局或功能
- 禁止使用占位符代替真实数据
- 禁止添加图片中不存在的功能验证

## 配置选项

### 1. 基本配置

**CLAUDE.md 配置示例：**

```markdown
# 测试用例生成器配置

## 基本配置
- output_format: markdown  # 仅支持 markdown
- template: default  # 使用默认模板
- language: zh-CN  # 支持 zh-CN、en-US

## 高级配置
- enable_test_data_generation: true  # 启用智能测试数据生成
- enable_quality_assessment: true  # 启用测试用例质量评估
- parallel_generation: true  # 启用并行生成
- enable_image_parsing: true  # 启用需求文档图片解析
- image_parsing_types:  # 要解析的图片类型
  - interface  # 界面设计图
  - flowchart  # 流程图
  - architecture  # 架构图
  - screenshot  # 示例截图

## 自定义字段
- custom_fields:
  - 模块
  - 子模块
  - 相关需求
  - 测试环境
```

### 2. 命令行参数

**支持的命令行参数：**

- `--format`: 指定输出格式（仅支持 markdown）
- `--template`: 指定使用的模板
- `--review`: 启用测试用例评审
- `--enable-image-parsing`: 启用需求文档图片解析
- `--image-types`: 指定要解析的图片类型，用逗号分隔（interface,flowchart,architecture,screenshot）
- `--help`: 显示帮助信息

## 使用方法

### 基本使用

1. 准备输入文件：
   - 需求文档（必选）：requirement/目录下的 PDF 或 DOCX 文件
   - 技术设计文档（可选）：requirement/目录下的 PDF、DOCX 或 MD 文件
   - CLAUDE.md（可选）：配置文件
2. 执行 /testcase-gen 命令
3. 生成的测试用例将保存在 test-case/{需求文档文件名}\_test\_cases.md 文件中

### 高级使用

1. **自定义模板：** 在 templates 目录下创建自定义模板文件
2. **测试用例评审：** 执行 /testcase-gen --review 命令
3. **版本控制：** 启用 enable\_version\_control 配置
4. **测试执行跟踪：** 在生成的测试用例中填写执行信息
