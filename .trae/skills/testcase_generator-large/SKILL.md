# 测试用例生成器（大文档版）

## 目标

针对大型需求文档（>=2M），采用分治策略：先按测试点独立生成测试用例，再合并到总用例文件。提高大文档处理效率，确保测试用例覆盖全面。

## 角色定位

作为拥有 10 年 + 企业级软件测试经验的资深测试工程师，掌握 AI 领域知识，精通测试和代码逻辑，擅长从需求文档和技术文档中全维度提取功能点、业务规则、约束条件、异常分支、边界场景、依赖逻辑，设计高覆盖率、无遗漏、可落地执行的测试用例。

## 业务注意点说明

- 当需求文档中有指定业务线/品牌/学科时,反向用例就是非该业务线时不显示该功能点或原有功能点保持不变。

## 核心原则

- **策略指导：** 提供判断标准，而非强制数量
- **场景驱动：** 基于实际场景复杂度生成用例
- **数据具体：** 测试数据必须具体，不用占位符
- **可验证性：** 预期结果必须明确可验证
- **灵活性：** 支持多种输入输出格式
- **可扩展性：** 支持自定义测试用例模板
- **智能管理：** 提供测试用例版本控制和复用功能
- **质量保证：** 内置测试用例质量评估机制
- **分治策略（大文档专属）：**
  - 先将需求文档按模块/测试点拆分为多个独立部分
  - 每个测试点独立生成测试用例
  - 最后将所有测试点的用例合并到总用例文件
- **强制图片解析（关键，不可以跳过）：**
  - **必须提取并分析需求文档中的所有图片**
  - **测试数据必须来源于图片中的真实数据**（如：学员ID、课包ID、liveid、时间、金额等）
  - **界面验证必须基于截图中的实际布局**（字段名称、按钮位置、表格列名等）
  - **业务流程必须基于流程图中的实际步骤**
  - **禁止凭空想象功能或数据**

## 核心测试设计方法

### 1. 等价类划分法

将输入数据划分为若干等价类,从每类中选取代表性数据测试。

**应用示例:**
**用户名密码登录**

**输入项:** 用户名、密码

**用户名等价类:**

- 有效: \[6-20字符,字母数字下划线] → "test\_user123"
- 无效: \[<6] "ab" | \[>20] "verylongusername12345" | \[特殊字符] "user\@name" | \[空] ""

**密码等价类:**

- 有效: \[8-20字符,含大小写+数字] → "Test1234"
- 无效: \[<8] "Test12" | \[缺大写] "test1234" | \[空] ""

**生成原则:** 一次测试一个等价类,其他保持有效

### 2. 边界值分析法

边界是最容易出错的地方。

**边界三点法:** 离点(min-1) | 上点(min) | 内点(中间值) | 上点(max) | 离点(max+1)

**应用示例:**
**用户名长度 6-20 字符:**

- 离点-下: 5字符 "abcde" → 失败
- 上点-下: 6字符 "abcdef" → 成功
- 内点: 13字符 "test\_user\_123" → 成功
- 上点-上: 20字符 "test\_user\_1234567890" → 成功
- 离点-上: 21字符 "test\_user\_12345678901" → 失败

**0 值法:**

**应用场景:** 部分属性为0 后则不再显示后续操作的场景（如学员详情中，课时为0 则不再显示课时明细链接）

### 3. 因果图法

通过分析输入条件之间的因果关系，生成测试用例。

**应用场景:** 输入条件之间存在逻辑关系（如 AND、OR、NOT）的场景

### 4. 判定表法

将输入条件和输出结果以表格形式列出，生成测试用例。

**应用场景:** 输入条件较多且组合复杂的场景

### 5. 场景法

基于用户实际使用场景生成测试用例。

**应用场景:** 业务流程复杂的场景

### 6. 错误推测法

基于经验和直觉推测可能的错误场景。

**应用场景:** 无法通过其他方法覆盖的异常场景

### 7. 用例数量判断

不强制数量，根据场景复杂度自适应调整。

**判断标准：**

- **输入项数量：** 输入项越多，用例越多
- **业务规则复杂度：** 规则越复杂，用例越多
- **风险等级：** Critical 和 High 需要更多用例
- **测试关注点：** 关注点越多，用例越多
- **测试类型：** 不同测试类型需要不同数量的用例

**推荐用例数量范围：**

- **简单场景：** 3-5个用例
- **中等场景：** 5-10个用例
- **复杂场景：** 10-20个用例

### 1. Markdown文本协议格式 (v0.4)

每个测试点生成一个临时 .md 文件,格式如下:

```markdown

## 模块名称

### 功能名称

#### 【P0】测试用例标题
##### 前置条件
- 前置条件1
- 前置条件2

##### 操作步骤
- 操作步骤1
- 操作步骤2
- 操作步骤3

##### 预期结果
- 预期结果1
- 预期结果2
- 预期结果3
```

### 5. 字段说明

markdown文件root节点：直接使用【测试点名称】，临时文件使用测试点名称，最终合并文件使用【需求名称】

**优先级：** P0-P2（必填）

- P0（核心必测）：系统核心业务流程、主功能、数据准确性的测试点，不通过则功能无法正常使用；冒烟用例仅从P0优先级中选取，聚焦最核心、最基础的流程验证，确保系统能正常启动、核心功能可正常使用。
- P1（重要验证）：影响功能使用体验、辅助功能正常运行的测试点，不通过不阻断核心流程但影响使用；此类用例不设为冒烟用例。
- P2（次要检查）：界面展示、非核心交互、边缘场景的测试点，不通过对业务流程无实质影响；此类用例不设为冒烟用例

**\反向-：** 反向用例标记（可选）

**测试类型：** 功能、接口、性能、安全、兼容、易用、安装部署、可靠、本地化、可维护、可扩展、配置（12选1）

**前置条件：** 测试前的准备工作

**测试步骤：** 操作步骤，每个步骤占一行

**预期结果：** 期望的结果，与步骤一一对应

### 6. 测试数据要求

**使用用占位符：**

### 7. 预期结果要求

**必须明确可验证：**

**正确示例：**

- 跳转到 /home 页面，顶部显示"欢迎，test\_user"
- 提示"密码长度不足，请输入8-20位密码"

**错误示例：**

- 登录成功
- 提示错误信息
- 系统正常处理

## 大文档用例生成流程（分治策略）

### Step 0: 检测文档大小

1. 扫描 requirement 目录下所有文档
2. 计算所有文档的总大小
3. 如果总大小 >= 2MB：使用此 skill
4. 如果总大小 < 2MB：使用原 skill

### Step 1: 准备上下文

1. 检测 requirement 目录下的需求文档格式（PDF 或 DOCX）
2. 读取需求文档内容，包括文本和图片
3. **【强制】解析需求文档中的图片**（必须执行，不可跳过）：
   - 提取所有嵌入图片（PNG、JPG、JPEG 等格式）
   - 识别图片类型：界面截图、流程图、架构图、示例数据等
   - 保存图片到临时目录供后续分析使用
   - **必须分析图片内容并用于生成测试用例**
4. 读取 requirement 目录下的技术设计文档（如果存在），包括其中的图片
5. 读取配置文件（如果存在）
6. 提取需求文档文件名作为输出文件前缀
7. 加载自定义模板（如果有）
8. 创建 test-case/points/ 目录（用于存放测试点临时文件）

### Step 2: 理解需求并拆分测试点

1. 分析需求文档文本内容，识别功能点和业务规则
2. **【强制】必须分析需求文档中的图片**，提取以下信息：
   - **界面截图**：提取页面布局、字段名称、按钮位置、数据格式、消息内容、提醒文案等
   - **流程图**：提取业务流程步骤、判断条件、分支逻辑等
   - **示例数据**：提取真实数据值（ID、名称、时间、金额、组织架构路径等）
   - **架构图**：提取系统模块关系、数据流向、组织架构层级等
3. **【关键】将需求文档拆分为独立的测试点**：
   - 按模块/功能拆分
   - 每个测试点相对独立
   - 测试点之间的依赖关系要明确
4. 列出所有测试点清单，例如：
   - 测试点1：融合LP-全局配置-自动加微LP名单配置
   - 测试点2：融合LP-学员详情-编辑资料
   - 测试点3：CSD-教务工作台-测评配置
   - 测试点4：北冥系统-对话管理系统-机器人管理
   - 测试点5：北冥系统-对话管理系统-意图管理
   - 测试点6：企微侧边栏-数学学员
   - 测试点7：班班Agent-首联
   - 测试点8：班班Agent-测评
   - 测试点9：班班Agent-选班
   - 测试点10：六一工作台-企微群发任务配置
   - 测试点11：北极星系统-任务配置
   - 测试点12：融合LP-待办任务
   - 测试点13：企微用户备注
   - 测试点14：自动加微流程

### Step 3: 逐个测试点生成用例

对每个测试点独立执行以下步骤：

#### Step 3.1: 理解当前测试点

- 聚焦当前测试点的功能范围
- 提取该测试点的输入项
- 识别该测试点的业务规则和约束条件

#### Step 3.2: 选择测试设计方法

根据当前测试点复杂度选择合适的测试设计方法：

- 简单场景：等价类划分法 + 边界值分析法
- 复杂场景：因果图法 + 判定表法
- 流程场景：场景法
- 特殊场景：错误推测法

#### Step 3.3: 生成测试用例

基于选择的测试设计方法生成测试用例：

- 核心功能：覆盖有效等价类
- 异常场景：覆盖无效等价类
- 边界条件：覆盖边界值
- 组合场景：覆盖输入项组合
- 流程场景：覆盖完整业务流程
- 异常场景：覆盖可能的错误情况

#### Step 3.4: 验证测试用例

- 检查测试用例的完整性
- 检查测试数据的具体性
- 检查预期结果的可验证性
- 检查测试用例的覆盖度
- 评估测试用例的质量

#### Step 3.5: 保存测试点临时文件

- 将当前测试点的用例保存到 test-case/points/{测试点名称}\_test\_cases.md
- 按照指定格式编写用例
- 确保测试数据具体、预期结果可验证

### Step 4: 合并所有测试点用例

1. 读取 test-case/points/ 目录下所有测试点临时文件
2. 按模块和功能点组织所有用例
3. 合并成一个完整的测试用例文件
4. 保存到 test-case/{需求文档文件名}\_test\_cases.md
5. 保持用例格式的一致性
6. 清理临时文件（可选）

### Step 5: 最终验证

- 检查总用例文件的完整性
- 检查模块和功能点的组织是否合理
- 检查用例之间的逻辑一致性
- 评估整体测试用例质量

## 高级功能

### 1. 自定义模板

支持用户自定义测试用例模板，通过修改 templates 目录下的模板文件或在 CLAUDE 文件中配置模板。

### 2. 批量生成

支持批量生成多个测试点的测试用例，自动处理多个 ITEM 和 POINT，支持并行生成以提高效率。

### 3. 测试用例评审

生成测试用例后，提供评审功能，检查测试用例的质量和覆盖度，生成评审报告。

### 4. 测试执行跟踪

支持在测试用例中添加执行状态和结果，便于跟踪测试执行情况，生成测试执行报告。

### 5. 智能测试数据生成

根据输入项的约束条件，智能生成符合要求的测试数据，提高测试数据的质量和覆盖度。

### 6. 测试用例质量评估

内置测试用例质量评估机制，从完整性、可验证性、覆盖度等方面评估测试用例的质量。

### 7. 需求文档图片解析（强制）

**必须解析需求文档中的所有图片**，这是生成准确测试用例的关键步骤：

**图片提取流程：**

1. **自动提取**：从 PDF/DOCX 文档中提取所有嵌入图片
2. **图片分类**：
   - 界面截图：识别页面布局、功能模块、数据表格
   - 流程图：识别业务流程、判断节点、分支路径
   - 架构图：识别系统组件、数据流向、接口关系
   - 示例数据：识别真实数据值、字段格式、计算逻辑
3. **内容识别**：
   - 读取截图中的文字内容（OCR）
   - 识别表格结构和数据
   - 提取界面元素（按钮、输入框、标签页等）

**图片信息应用：**

- **测试数据**：必须使用图片中的真实数据（ID、名称、时间、金额等）
- **操作步骤**：必须按照截图中的实际界面元素编写
- **预期结果**：必须验证截图中显示的实际字段和布局
- **业务流程**：必须遵循流程图中的实际步骤

**禁止行为：**

- 禁止忽略需求文档中的图片
- 禁止凭空想象界面布局或功能
- 禁止使用占位符代替真实数据
- 禁止添加图片中不存在的功能验证

## 配置选项

### 1. 基本配置

**CLAUDE.md 配置示例：**

```markdown
# 测试用例生成器配置（大文档版）

## 基本配置
- output_format: markdown  # 仅支持 markdown
- template: default  # 使用默认模板
- language: zh-CN  # 支持 zh-CN、en-US
- enable_split_by_points: true  # 启用按测试点拆分

## 高级配置
- enable_test_data_generation: true  # 启用智能测试数据生成
- enable_quality_assessment: true  # 启用测试用例质量评估
- parallel_generation: true  # 启用并行生成（多个测试点并行）
- enable_image_parsing: true  # 启用需求文档图片解析
- image_parsing_types:  # 要解析的图片类型
  - interface  # 界面设计图
  - flowchart  # 流程图
  - architecture  # 架构图
  - screenshot  # 示例截图
- keep_temp_files: false  # 是否保留测试点临时文件

## 自定义字段
- custom_fields:
  - 模块
  - 子模块
  - 相关需求
  - 测试环境
```

### 2. 命令行参数

**支持的命令行参数：**

- `--format`: 指定输出格式（仅支持 markdown）
- `--template`: 指定使用的模板
- `--review`: 启用测试用例评审
- `--enable-image-parsing`: 启用需求文档图片解析
- `--image-types`: 指定要解析的图片类型，用逗号分隔（interface,flowchart,architecture,screenshot）
- `--keep-temp`: 保留测试点临时文件
- `--help`: 显示帮助信息

## 使用方法

### 基本使用

1. 准备输入文件：
   - 需求文档（必选）：requirement/目录下的 PDF 或 DOCX 文件
   - 技术设计文档（可选）：requirement/目录下的 PDF、DOCX文件&#x20;
   - CLAUDE.md（可选）：配置文件
2. 执行 /testcase-gen-large 命令（或自动检测文档大小 >= 2M 时自动触发）
3. 系统按测试点逐个生成用例到 test-case/points/ 目录
4. 系统自动合并所有测试点用例到 test-case/{需求文档文件名}\_test\_cases.md

### 高级使用

1. **自定义模板：** 在 templates 目录下创建自定义模板文件
2. **测试用例评审：** 执行 /testcase-gen-large --review 命令
3. **保留临时文件：** 执行 /testcase-gen-large --keep-temp 命令
4. **版本控制：** 启用 enable\_version\_control 配置
5. **测试执行跟踪：** 在生成的测试用例中填写执行信息

## 与原 skill 的区别

| 特性     | testcase-generator（原） | testcase-generator-large（新） |
| ------ | --------------------- | --------------------------- |
| 适用文档大小 | < 2MB                 | >= 2MB                      |
| 生成策略   | 一次性生成                 | 按测试点拆分，逐个生成后合并              |
| 内存占用   | 较高                    | 较低（分治策略）                    |
| 处理效率   | 大文档较慢                 | 大文档更快                       |
| 临时文件   | 无                     | 有（test-case/points/）        |
| 可恢复性   | 较低                    | 较高（可从临时文件恢复）                |
